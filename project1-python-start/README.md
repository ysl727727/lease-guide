## 2. 실행 방법

### 준비
```powershell
uv sync
ollama pull gemma3:4b
ollama pull qwen3:4b-instruct-2507-q4_K_M
```

### 로컬 실험 (모델 2개 × 질문 10개 × 2회 = 40회)
```powershell
ollama stop gemma3:4b
ollama stop qwen3:4b-instruct-2507-q4_K_M
ollama ps                          # 목록이 비어 있어야 함
uv run python run_experiment.py
```

한 문항만 시험 실행할 때:
```powershell
uv run python run_experiment.py --only Q01 --out results/pilot.jsonl
```

```powershell
uv run python run_cloud.py
```
API 키는 실행 중 입력받으며 코드·저장소·로그에 저장하지 않습니다.

## 4. 실험 조건

모든 질문·모든 모델에 동일하게 적용했습니다.

```python
OPTIONS = {"temperature": 1, "num_predict": 1024, "num_ctx": 4096}
```

- system 프롬프트 동일, 출력 형식 강제 (`판정:` / `유형:` / `근거:`)
- 질문마다 messages를 새로 생성 (이전 질문의 대화 이력을 잇지 않음)
- 판정 기준을 프롬프트에 직접 제공 (검색·RAG 없음)
- 모델당 워밍업 1회는 `is_warmup: true`로 표시하고 본 집계에서 제외
- 실패 회차는 `status: "error"`로 기록하며 삭제하거나 재시도 결과로 덮어쓰지 않음
- 측정값이 없으면 `null`로 두며 0으로 채우지 않음
- 답변에 판정이 여러 번 등장하면 첫 번째 `판정:` 줄을 공식 출력으로 채점

### temperature 1 / seed 미지정으로 정한 이유
Cloud 모델(`gpt-5.6-luna`)은 temperature 0을 지원하지 않고 기본값 1만 허용하며,
seed도 지정하지 않은 상태였습니다. 1차 실험(로컬 temperature 0 / seed 42)에서는
Local–Cloud 생성 설정이 일치하지 않았습니다.

조건을 맞추기 위해 로컬을 temperature 1 / seed 미지정으로 변경하고 전체를
재실행했습니다. seed를 양쪽에 42로 넣는 방안도 검토했으나, 실행 환경이 달라 같은
값을 넣어도 재현이 연결되지 않으므로 양쪽 미지정이 조건 일치에 부합한다고
판단했습니다.

부수 효과로, 질문별 2회 반복이 답변 편차를 관측할 수 있게 됐습니다.
1차에서는 19개 문항이 토큰 단위로 동일해 반복의 의미가 제한적이었습니다.

### 6-2. 성능 (본 실험 20회 기준, 지표별 n=20)

| 지표 | gemma3 | qwen3 |
|---|---|---|
| 전체 응답 시간 | **1.45초** (0.96~1.96) | 1.94초 (1.03~6.76) |
| 생성 속도 | 83.69 tok/s (69.4~102.3) | **101.99 tok/s** (98.56~104.51) |
| 출력 토큰 수 | 107.2 (87~132) | 190.15 (93~655) |
| 입력 토큰 수 | 474.4 (376~555) | 540.2 (415~638) |
| VRAM | **2742.3 MiB** | 3030.9 MiB |
| 모델 로딩 (워밍업 1회) | 3.904초 | **1.826초** |

해석 시 주의
- 응답 시간 차이는 출력 길이에서 옵니다. 초당 생성 속도는 qwen3가 약 20% 빠릅니다.
- 본 실험의 `load_duration`은 모두 0.001~0.002초로, 이미 메모리에 올라온 상태의 값입니다. 로딩 시간 비교에는 워밍업 값을 사용했습니다.
- qwen3의 최대 응답 시간 6.76초는 Q06 1회차(655토큰)입니다.
- 토크나이저가 달라 입력 토큰 수가 다르므로, tokens/s만으로 체감 속도를 비교할 수 없습니다.
- `size_vram`은 각 응답 직후 관측한 시점의 값이며 최대 VRAM 사용량이 아닙니다.
- 전체 응답 시간을 TTFT로 표기하지 않습니다. 첫 토큰 지연은 별도 측정하지 않았습니다.
- gemma3의 tokens/s는 Q01~Q06 구간 67~80, Q07 이후 약 102로 변동했습니다. 1·2차 실험 모두 같은 지점에서 재현됐으며, 장비 상태의 영향으로 보입니다.

실패 회차: 없음 (40/40 성공)

## 7. Local vs Cloud 비교

### 7-1. 공통 5문항 품질 (Q01, Q03, Q05, Q06, Q10)

Cloud 비교 질문 5개는 **결과를 보기 전에** 10개 세트에서 선정했습니다
(정상 3 / 경계 1 / 범위밖 1로 원래 비율 유지).

| 문항 | gemma3 | qwen3 | cloud-luna |
|---|---|---|---|
| Q01 | 50% | 100% | 100% |
| Q03 | 75% | 100% | 100% |
| Q05 | 30% | 100% | 100% |
| Q06 | 25% | 50% | 100% |
| Q10 | 33.3% | 33.3% | 100% |
| **평균** | 42.7% | 76.7% | **100%** |

**반복 수: 로컬 각 2회(모델당 10회) / Cloud 각 1회(5회)**
호출 성공 수 / 전체 시도 수: gemma3 10/10, qwen3 10/10, cloud-luna 5/5

Cloud만 통과한 문항이 둘입니다.
- **Q06**: 45도가 90도 미만임을 세 문장으로 정리하고 종료 (80토큰). qwen3는 655토큰을 쓰고도 판정 줄을 틀렸습니다.
- **Q10**: 광고 판정은 하되 손해배상·승소 가능성은 판단 범위 밖임을 명시했습니다. 로컬 두 모델 모두 실패했습니다.

### 7-2. 주요 비교 기준

| 기준 | Local (qwen3) | Cloud (gpt-5.6-luna) | 구분 |
|---|---|---|---|
| Quality | 공통 5문항 76.7% (n=10) | 공통 5문항 100% (n=5) | 실측 |
| Latency | 평균 1.94초 (n=20) | 평균 2.53초 (n=5) | 실측 |
| Cost | 호출 요금 없음. 장비·전력·관리 비용 별도 발생 | 5회 $0.00117 (입력 $0.20 / 출력 $1.20 per 1M) | 실측 |
| Security | 매물·중개사 정보가 외부로 나가지 않음 | 외부 API로 전송됨 | 분석 |
| Infrastructure | RTX 5060 8GB 노트북 필요. 모델 다운로드·서빙 관리 | 별도 장비 불필요 | 분석 |
| Customization | 모델·프롬프트·생성 설정 전부 통제 가능 | 제공자가 지원하는 범위로 제한 (temperature 0 불가) | 분석 |
| Operations | Ollama 설치 후 첫 시도에 동작 | 3회 실패 후 성공: ① 모델 접근 권한 없음(403) ② `max_tokens` 미지원(400) ③ `temperature=0` 미지원(400) | 실측 |

- 품질·응답 시간·토큰 사용량은 **실측 결과**, 데이터 통제·인프라·운영 부담은 **서비스 요구사항과 확인한 조건에 따른 분석**입니다.
- 응답 시간에는 각 실행 환경과 네트워크 조건의 영향이 포함되어 있습니다.
- 로컬 운영에도 장비·전력·관리 비용이 있으므로, 호출 요금이 없다는 이유만으로 총비용을 0원으로 표기하지 않습니다.
- Cloud 사용량과 단가로 계산한 추정 비용이며, 실제 사용 내역은 OpenAI 대시보드에서 별도 확인합니다.
- Local/Cloud는 실행 위치 구분이고, 공개 가중치/License는 이용 조건 구분입니다. 두 후보 모두 공개 가중치 모델을 로컬에서 실행했습니다.

### 7-3. 조건 일치 여부

**맞춘 것**: system 프롬프트, 자료, messages 구조, temperature 1, seed 미지정, 출력 한도 1024

**맞출 수 없는 것**
- 반복 수(로컬 2회 / Cloud 1회)와 질문 수(10개 / 5개) — 발제 지정
- context 길이: 로컬은 `num_ctx` 4096 명시, Cloud는 지정 불가
- 출력 한도 파라미터명이 다름 (`num_predict` / `max_completion_tokens`)
- 실행 환경: 로컬 GPU vs 원격 서버 + 네트워크
- 모델 규모: 4B vs 미공개

### 9-2. 발제 질문에 대한 답

**VRAM은 얼마나 감소하는가**
4bit는 8bit 대비 1700.5 MiB 적게 씁니다(3030.9 vs 4731.4). 정밀도를 두 배 올렸지만
VRAM은 1.56배만 늘었는데, KV 캐시 등 양자화와 무관한 영역이 있기 때문입니다.
8GB VRAM 기준으로 q8_0도 100% GPU 적재가 가능했습니다.

**속도에는 어떤 차이가 발생하는가**
q4_K_M이 빠릅니다. 평균으로는 21% 차이지만, 실제 격차는 더 큽니다.
q4 측정값은 69.7~103.1로 폭이 넓은데, Q01~Q04 구간이 70~78이고 Q05 이후 101~103입니다.
먼저 실행되어 장비 워밍업 구간이 섞였습니다. q8은 68.31~71.68로 일정합니다.
**안정 구간끼리 비교하면 q4 약 102 vs q8 약 70으로 q4가 약 45% 빠릅니다.**

**모델 품질에는 어떤 변화가 생기는가**
**의미 있는 차이가 관측되지 않았습니다.** 82.5% vs 79.7%로 2.8%p 차이인데,
같은 q4_K_M을 기본 실험에서 측정했을 때는 75.6%였습니다(이번 82.5%).
**같은 모델·같은 설정의 회차 간 편차가 6.9%p**로, 양자화 간 차이보다 큽니다.
따라서 이 실험에서 정밀도를 높인 효과는 확인되지 않았습니다.

### 9-3. 관측된 질적 차이

**숫자 생성 오류가 q4에서만 나타났습니다.**
- Q03: q4는 두 회차 모두 `400m`를 "40 지표", "40 지점"으로 잘못 생성. q8은 두 회차 모두 정확
- Q06 1회차: q4에서 "9-도 이상" 토큰 깨짐

**출력 한도 도달도 q4에서만 발생했습니다.**
Q06 1회차에서 q4는 동일 논리를 10회 이상 반복하다 1024토큰에 도달해 절단됐습니다.
q8은 279/543토큰으로 종료했습니다.

**q8은 유형 칸 오류가 있었습니다.**
Q02 1회차와 Q04 2회차에서 근거는 (다)를 정확히 인용했으나 유형 칸에 '부존재·허위'를
기입했습니다(정답은 거짓·과장). q4는 이 오류가 없었습니다.

### 9-4. 결론

이 Use Case에서는 **q4_K_M이 합리적인 선택입니다.**
VRAM을 1.7 GB 덜 쓰고, 생성이 빠르며, 품질 차이는 회차 편차 범위 안에 있습니다.

다만 표본이 40건이고 두 버전 모두 같은 문항(Q06, Q08)에서 실패했으므로,
정밀도를 높여도 해결되지 않는 한계가 있다는 점이 함께 확인됐습니다.
숫자 생성 오류와 출력 한도 도달이 q4에서만 나타난 점은 추가 관찰이 필요합니다.

## 10. 선택 실습 B — 임베딩 실험

Sentence Transformers로 문장을 임베딩 벡터로 바꾸고 코사인 유사도를 확인했습니다.
후속 검색·RAG 학습을 위한 선택 실습이며, 필수 결과에는 포함하지 않습니다.

- 스크립트: `embedding_test.py`
- 모델: `paraphrase-multilingual-MiniLM-L12-v2` (384차원)
- 흐름: 문장 → 임베딩 벡터 → 코사인 유사도 → 의미 유사도 확인

### 10-1. 발제 예시 문장

기준: "고양이가 소파 위에 있다."

| 비교 문장 | 유사도 |
|---|---|
| 소파 위에 고양이가 앉아 있다. | **0.9509** |
| 오늘 주식시장이 상승했다. | −0.011 |

어순이 바뀌고 표현이 달라도 의미가 같으면 벡터 공간에서 가깝고,
무관한 문장은 음수까지 떨어집니다.

### 10-2. 프로젝트 자료에 적용

판정 기준 네 조항 중 광고 사례와 의미상 가까운 것을 찾을 수 있는지 확인했습니다.

**사례 1 — 방향 (정답: (다))**

| 조항 | 유사도 |
|---|---|
| **(다) 방향이 90도 이상 차이** | **0.6791** |
| (라) 직선거리 표시 | 0.6329 |
| (가) 옵션 성능 | 0.5896 |
| (나) 관리비 차이 | 0.4269 |

정답 조항이 1위였으나 2위와 차이가 0.046에 불과합니다.

**사례 2 — 직선거리 (정답: (라))**

| 조항 | 유사도 |
|---|---|
| (다) 방향이 90도 이상 차이 | 0.3573 |
| **(라) 직선거리 표시** | 0.3298 |
| (나) 관리비 차이 | 0.2787 |
| (가) 옵션 성능 | 0.2143 |

**정답 조항이 2위로 밀렸습니다.** 전체 점수대도 0.21~0.36으로 사례 1의 절반 수준입니다.
사례는 "지하철역·도보 5분·13분", 조항은 "주요 교통시설·도보거리·직선거리"로
의미는 같으나 어휘가 겹치지 않습니다. 반면 (다)는 "광고했으나 실제로는"이라는
문장 구조가 사례와 닮아 더 높게 나왔습니다.

### 10-3. 관찰

**단순 임베딩 유사도만으로는 법 조항 매칭이 신뢰할 수준이 아닙니다.**
2건 중 1건에서 오답 조항이 1위였습니다.

이번 프로젝트가 자료를 프롬프트에 직접 제공하는 방식(in-context QA)을 택한 것이
결과적으로 이 위험을 피한 셈입니다. 향후 RAG를 도입한다면 검색 단계의 정확도를
별도로 평가해야 하며, 유사도 값을 판정의 사실성 점수로 해석해서는 안 됩니다.

이 실습은 생성 모델의 내부 토큰 표현이 아니라 문장 비교용 임베딩을 사용했고,
같은 임베딩 모델·같은 설정으로 얻은 벡터끼리만 비교했습니다.
Vector DB나 RAG 시스템은 구현하지 않았습니다.

- Q07은 2026년 7월 개정으로 요건이 바뀐 사안입니다. 두 모델 모두 이 개정 내용을 학습했을 가능성은 낮으므로, 관찰된 차이는 사전 지식의 차이가 아니라 제공된 자료의 조건절을 판정에 반영하는 능력의 차이로 해석했습니다.
- Cloud 모델(`gpt-5.6-luna`)의 파라미터 규모와 학습 조건이 공개되지 않아, 품질 차이를 모델 크기 차이로 단정할 수 없습니다.
- 사용한 고시는 제2026-345호(2026.7.3.)로 고정했습니다. 조문 번호 대신 (가)(나)(다) 라벨로 제시해 인용 오류 가능성을 줄였습니다.
- 채점은 AI 도움없이 진행했습니다. 같은 기준으로 재검토했으나 교차 확인은 하지 못했습니다.

## 12. 운영 방식 권고

최종 로컬 모델 선정과 별개로, 실제 서비스에는 단계적 구성을 제안합니다.

공통 5문항에서 Cloud는 100%, qwen3는 76.7%였습니다. 격차는 경계 사례(Q06)와
범위 밖 요청(Q10)에서 발생했고, 정상 사례에서는 qwen3도 100%였습니다.

- **1차 선별은 로컬(qwen3)** — 미검수 매물 정보와 중개사 정보가 외부로 나가지 않습니다. 명확한 위반 유형은 로컬로 충분히 처리됩니다.
- **경계·모호 사례는 사람 검토로 넘김** — 판단 유보가 필요한 상황에서 로컬 모델이 결론을 강제로 내리는 경향이 확인됐습니다. 신뢰도가 낮은 판정을 사람에게 넘기는 장치가 필요합니다.
- **출력 형식 검증 장치 필요** — qwen3도 Q06에서 판정 블록을 2회 출력하고, Q07에서 유형 칸을 잘못 채웠습니다. 파싱 실패나 판정 모순을 걸러내는 후처리가 있어야 합니다.
- **비용은 로컬 선택의 주된 이유가 아닙니다** — Cloud 5회 $0.00117 수준이라 호출 요금 자체는 부담이 크지 않습니다. 로컬을 택하는 근거는 데이터 통제입니다.
- **법적 판단 요청 차단** — gemma3가 Q10에서 소송 가능성을 언급한 사례처럼, 안내 범위를 벗어난 질문은 모델에 맡기지 말고 입력 단계에서 걸러내는 편이 안전합니다.
