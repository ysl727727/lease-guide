# 프로젝트 노트 — 허위매물 탐지 어시스턴트

## STEP 1. 문제 정의

**허위매물 탐지 어시스턴트**

매물 광고 정보를 국토교통부고시 「부당한 중개대상물 표시·광고행위의 유형 및 기준」
(제2026-345호, 2026.7.3. 일부개정)에 대조해 부당 표시·광고 해당 여부와 유형을
판정하는 어시스턴트에 사용할 로컬 모델을 선정한다.

- 사용자: 부동산 플랫폼 매물 검수 담당자
- 답해야 할 질문: 광고가 고시 기준에 해당하는지, 어느 유형인지, 근거는 무엇인지
- 한국어 성능: 중요 (기준·광고·판정이 모두 한국어)
- 데이터 통제: 미검수 매물 정보와 중개사 정보가 포함되므로 로컬 운영에 근거가 있음
- 응답 속도: 중요도 중간 (실시간 대화가 아닌 검수 배치 작업)
- GPU 환경: RTX 5060 Laptop 8GB

**자료 제공 방식**: 고시 조항을 프롬프트에 직접 포함. 검색·RAG 없음(in-context QA).

**Q07 설계 의도**: 자료에 "기망 행위가 확인된 경우"라는 요건이 있고, 사례는 그

어긋나도록 설계해, 모델이 자료의 조건절을 판정에 반영하는지를 본다.

### 통제 조건
- system 프롬프트: 10개 질문 전체, 두 모델 모두 동일
- 출력 형식 강제: `판정:` / `유형:` / `근거:` 3줄
- 질문마다 messages를 새로 생성. 이전 질문의 대화 이력을 이어 붙이지 않음
- 답변에 판정이 여러 번 등장하면 **첫 번째 '판정:' 줄을 공식 출력**으로 본다.
  자동화 파이프라인이 그 줄을 파싱하기 때문이다.

### 채점 방식
- `questions.json`의 `expected` 체크리스트 항목당 1점
- 질문마다 만점이 다르므로 **획득/만점 = 달성률(%)** 로 환산해 비교
- 점수와 함께 근거가 된 응답 문장을 인용해 기록
- 호출 성공 여부와 답변 품질 통과 여부는 구분해 기록
- 2차 실험부터 `verdict` 열을 추가해 모델이 실제로 출력한 판정값을 기록

### 채점 항목 수정 (채점 중 발견)
Q09·Q10의 `expected`에 있던 '확인처를 안내했는가' 항목을 채점에서 제외했다.

### 1차 실험 — `results/archive_temp0/` (본 집계 제외)
- 생성 설정: temperature **0**, num_predict 1024, num_ctx 4096, **seed 42**
- 결과: 40/40 성공. gemma3 55.1% / qwen3 85.0%
- Cloud 5회 성공, 공통 5문항 100%
- **제외 사유**: Cloud 모델(gpt-5.6-luna)이 temperature 0을 지원하지 않아 기본값 1로
  실행되고 seed도 지정하지 않아, 로컬(temperature 0 / seed 42)과 생성 설정이 달랐다.
  Local–Cloud 비교 조건을 맞추기 위해 로컬을 temperature 1 / seed 미지정으로 변경하고
  전체를 재실행했다.
- 그 밖에 포함된 기록: `runs_np512*.jsonl`(출력 한도 512에서 절단 발생 → 1024로 상향),
  `cloud_failed_*.jsonl`(Cloud API 파라미터 규격 문제로 실패한 시도)

### 2차 실험 (본 집계 대상)
- 생성 설정: temperature **1**, num_predict 1024, num_ctx 4096, **seed 미지정**
- 로컬: `results/runs.jsonl` — 40/40 성공, 실패 없음
- Cloud: `results/cloud.jsonl` — 5/5 성공, 추정 비용 $0.00117
- 품질: gemma3 50.1% / qwen3 75.6% / cloud-luna 100%(공통 5문항)

### seed를 제거한 이유
로컬과 Cloud 양쪽에 seed 42를 넣는 방안도 검토했으나, 실행 환경이 달라 같은 값을
넣어도 재현이 연결되지 않는다. Cloud 쪽은 seed를 지정하지 않은 상태였으므로,
양쪽 모두 미지정으로 맞추는 것이 조건 일치에 부합한다고 판단했다.
seed를 유지하면 temperature 1이어도 답변이 고정되어, 질문별 2회 반복이
답변 편차를 보여주지 못한다는 점도 고려했다.

## 관찰 사항

### temperature 변경이 점수에 미친 영향
| | 1차 (temp 0) | 2차 (temp 1) | 변화 |
|---|---|---|---|
| gemma3 | 55.1% | 50.1% | −5.0%p |
| qwen3 | 85.0% | 75.6% | −9.4%p |

두 모델 모두 하락했고 qwen3의 하락폭이 크다. 특히 범위밖 유형이 75.0% → 54.2%로
떨어졌는데, Q09 1회차에서 과태료가 자료에 없다는 안내를 누락한 것이 원인이다.
1차에서는 두 회차가 동일해 관측되지 않았던 편차다.

gemma3는 경계·범위밖 유형 점수가 1차와 동일하다. 원래 낮아 추가 하락 여지가 적었다.

### temperature 0과 1에서 동일하게 재현된 실패
- **Q05 (gemma3)**: 판정 칸에 유형 선택지 '해당없음'을 기입. 1회차는 유형 칸에
  선택지 4개를 그대로 복사 출력. 두 조건에서 점수가 1/5, 2/5로 완전히 동일하다.
  생성 설정의 문제가 아니라 모델이 판정 칸과 유형 칸을 구분하지 못하는 특성으로 판단된다.
- **Q06 (gemma3)**: "45도 차이가 나므로 90도 이상 차이에 해당한다"는 숫자 비교 실패.
- **Q07 (gemma3)**: 요건 미충족을 나열하고도 반대 결론.
- **Q08 (양쪽)**: '현저하게'의 수치 기준이 없는데 단정.

### gemma3의 조항 인용 불안정
Q02·Q03에서 "광고 시 제시한 옵션의 성능을 실제와 다르게 표시한 경우"라는 동일한
첫 문장이 반복된다. 방향(Q02)과 직선거리(Q03)는 각각 다른 조항인데 같은 문구를 쓴다.
Q04는 1차·2차 모두 1회차가 (가) 가격 조항, 2회차가 (다) 사진 조항으로 갈렸다.

### qwen3의 유형 칸 오류
2차 Q07에서 판정은 '미해당'으로 정확했으나 유형 칸에 '부존재·허위'를 기입했다.
미해당이면 '해당없음'이어야 한다. 1차에서는 맞췄던 항목이다.

### 판단 유보 판단의 실패
qwen3는 기준이 명확한 Q06(90도)에서 '판단불가'로 갔고, 기준이 모호한 Q08('현저하게')에서는
단정적으로 판정했다. 유보가 필요한 상황과 아닌 상황을 반대로 처리한 셈이다.
Cloud만 Q06을 '미해당'으로, Q10에서 판단 범위 밖임을 정확히 구분했다.

### tokens/s가 실행 중 변동함
gemma3의 tokens/s가 Q01~Q06 구간 67~80, Q07 이후 약 102로 뛴다.
1차·2차 실험 모두 **같은 지점에서 재현**됐다. GPU 전력 상태나 장비 워밍업의
영향으로 보이며, 모델의 성능 차이로 해석해서는 안 된다.
qwen3는 전 구간 약 100~104로 일정했다.

→ 평균만 표시하면 이 변동이 묻히므로, 최소/최대와 함께 기록한다.

### 입력 토큰 수가 모델별로 다름
같은 질문인데 qwen3의 `prompt_eval_count`가 gemma3보다 60~90 토큰 많다.
토크나이저가 달라서 생기는 차이이며, tokens/s만으로 체감 속도를 비교하면 안 되는
이유다. 전체 응답 시간을 함께 본다.

### 출력 한도 도달
1차 실험(num_predict 512)에서 qwen3의 Q06 출력이 512에 도달해 문장 중간에 잘렸다.
1024로 상향한 뒤에도 1차에서는 다시 한도에 도달했으나, 2차(temperature 1)에서는
655/290 토큰으로 종료되어 한도에 걸리지 않았다.
한도를 더 올려도 같은 현상이 반복될 것으로 판단해 1024로 확정했으며,
지시 준수(근거 2~3문장) 실패로 보고 품질 점수에 반영했다.

### VRAM
- gemma3: 2742.3 MiB (전 회차 일관)
- qwen3: 3030.9 MiB (전 회차 일관)
- `client.ps()`의 `size_vram`을 각 응답 직후 조회한 값이며, 최대 VRAM 사용량이 아니다.

### 모델 로딩 시간
본 실험 20회의 `load_duration`은 모두 0.001~0.002초다. 모델이 이미 메모리에
올라온 상태에서 호출했기 때문이며 실제 로딩 시간이 아니다.
로딩 시간 비교는 워밍업 1회 값을 사용한다 (gemma3 3.90초 / qwen3 1.83초).

## Local–Cloud 비교

### 조건 일치 여부 (2차 실험 기준)
**맞춘 것**: system 프롬프트, 자료, messages 구조, temperature 1, seed 미지정, 출력 한도 1024

**맞출 수 없는 것**
- 반복 수 (로컬 2회 / Cloud 1회) — 발제 지정
- 질문 수 (로컬 10개 / Cloud 5개) — 발제 지정
- context 길이: 로컬은 num_ctx 4096 명시, Cloud는 지정 불가(모델 기본값)
- 출력 한도 파라미터명이 다름 (`num_predict` / `max_completion_tokens`)
- 실행 환경: 로컬 GPU vs 원격 서버 + 네트워크 → 응답 시간 직접 비교에 한계
- 모델 규모: 4B vs 미공개

1차 실험에 있던 생성 설정 불일치(temperature 0 vs 1, seed 42 vs 미지정)는 해소됐다.

### Cloud 호출 방식
2번 가이드 예제(`02_luna_chat.py`)는 Responses API를 사용하지만,
`run_cloud.py`는 로컬(Ollama)과 동일한 messages 구조를 유지하기 위해
Chat Completions API를 사용했다. system/user 역할 분리와 프롬프트 구성을
로컬과 같게 맞추기 위함이다.

### Cloud API 호출 시 발생한 실패 (운영 난이도 근거)
1. 프로젝트 키에 `gpt-4o-mini` 접근 권한 없음 (403)
2. `max_tokens` 미지원 → `max_completion_tokens` 사용 필요 (400)
3. `temperature=0` 미지원, 기본값 1만 허용 (400)

로컬 Ollama는 설치 후 첫 시도에 동작했다. Cloud는 제공자가 정한 파라미터 규격에
맞춰야 하며, 규격이 바뀌면 코드를 고쳐야 한다.

## 선택 실습 A — 양자화 비교 (수행 완료)

`qwen3:4b-instruct-2507`의 q4_K_M과 q8_0을 같은 질문·같은 설정으로 비교했다.
기록: `results/runs_quant.jsonl`, `results/scores_quant.csv`
기본 비교표에는 사용하지 않는다.

### 실행 조건
- 설정: temperature 1, num_predict 1024, num_ctx 4096 — 기본 실험과 동일
- 질문 10개 × 2회 × 2버전 = 40회, 호출 성공 40/40
- 두 버전 모두 `ollama ps`에서 100% GPU 적재 확인
- **양자화 수준만 다르고 나머지 조건은 전부 동일하다.** 서로 다른 모델의 차이를
  양자화 효과로 해석하지 않기 위해 같은 모델의 두 버전만 사용했다.

### 결과
| 지표 | q4_K_M | q8_0 |
|---|---|---|
| VRAM | 3030.9 MiB | 4731.4 MiB (+1700.5, 1.56배) |
| 생성 속도 | 88.61 tok/s | 69.60 tok/s (−21%) |
| 품질 | 82.5% | 79.7% (−2.8%p) |
| 전체 응답 시간 | 2.42초 | 2.59초 |
| 출력 토큰 수 | 208.75 (95~1024) | 175.95 (95~543) |
| 로딩 시간 (워밍업) | 2.091초 | 4.498초 |

### 속도 비교 시 주의
q4의 측정값이 69.7~103.1로 폭이 넓다. Q01~Q04 구간이 70~78이고 Q05 이후 101~103인데,
먼저 실행되어 장비 워밍업 구간이 섞인 결과다. q8은 68.31~71.68로 일정하다.
안정 구간끼리 비교하면 q4 약 102 vs q8 약 70으로 q4가 약 45% 빠르다.
평균값(21% 차이)보다 실제 격차가 크다.

### 품질 차이의 해석
2.8%p 차이는 회차 편차보다 작다. 같은 q4_K_M을 기본 실험에서 측정했을 때는 75.6%였고
이번 양자화 실험에서는 82.5%였다. **같은 모델·같은 설정의 편차가 6.9%p**다.
따라서 "q4가 q8보다 품질이 높다"고 말할 수 없으며,
**정밀도를 높인 효과가 확인되지 않았다**는 것이 정확한 결론이다.

### 관측된 질적 차이
- **숫자 생성 오류가 q4에서만**: Q03에서 q4는 두 회차 모두 `400m`를 "40 지표",
  "40 지점"으로 잘못 생성. q8은 두 회차 모두 정확. Q06 1회차에서 q4는 "9-도 이상" 깨짐
- **출력 한도 도달도 q4에서만**: Q06 1회차에서 1024토큰 도달·절단. q8은 279/543토큰으로 종료
- **q8의 유형 칸 오류**: Q02 1회차, Q04 2회차에서 근거는 (다) 정확하나 유형 칸에
  '부존재·허위' 기입 (정답은 거짓·과장). q4는 이 오류가 없었다

### 결론
이 Use Case에서는 q4_K_M이 합리적이다. VRAM을 1.7 GB 덜 쓰고 생성이 빠르며
품질 차이는 회차 편차 범위 안에 있다. 다만 두 버전 모두 같은 문항(Q06, Q08)에서
실패했으므로 정밀도로 해결되지 않는 한계가 있다.
